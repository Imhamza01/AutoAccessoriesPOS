## BUG 1 (CRITICAL — SECURITY): JWT Secret hardcoded in source code

### Root Cause

This is committed to the source repository. Anyone who reads the code can forge valid JWT

### EXACT FIX — `src/backend/core/auth.py`

Find:
```python

```

Replace with:
```python
import os as _os

def _get_jwt_secret() -> str:
    """
    Load JWT secret from environment or generate+persist a secure one.
    Never use a hardcoded secret in production.
    """
    # 1. Check environment variable (set by deployment/installer)
    env_secret = _os.environ.get("POS_JWT_SECRET")
    if env_secret and len(env_secret) >= 32:
        return env_secret

    # 2. Check for a persisted secret file in the app data directory
    try:
        from pathlib import Path
        secret_dir = Path(_os.environ.get("APPDATA", Path.home())) / "AutoAccessoriesPOS"
        secret_dir.mkdir(parents=True, exist_ok=True)
        secret_file = secret_dir / ".jwt_secret"

        if secret_file.exists():
            stored = secret_file.read_text().strip()
            if len(stored) >= 32:
                return stored

        # 3. Generate a new secure secret and persist it
        import secrets as _secrets
        new_secret = _secrets.token_hex(32)  # 64-char hex string
        secret_file.write_text(new_secret)
        secret_file.chmod(0o600)  # Read/write for owner only
        import logging as _log
        _log.getLogger(__name__).info(
            f"Generated new JWT secret and stored at {secret_file}"
        )
        return new_secret

    except Exception as e:
        # Fallback: generate in-memory (tokens won't survive restart)
        import logging as _log
        _log.getLogger(__name__).warning(
            f"Could not persist JWT secret ({e}). "
            "Sessions will not survive server restart."
        )
        import secrets as _secrets
        return _secrets.token_hex(32)

JWT_SECRET = _get_jwt_secret()
```

## BUG 5: `_process_general_credit_payment` has no rollback on partial failure

### Root Cause
In `src/backend/api/credit_management.py`, `_process_general_credit_payment()` does:
1. UPDATE sales (multiple rows)
2. UPDATE customers
3. INSERT into customer_payments

If step 2 or 3 fails after step 1 completes, sales are marked as paid but the customer
balance is not reduced and no payment record exists. The `get_cursor()` context manager
does commit on success, but if an exception is raised mid-function, it depends on whether
the context manager does rollback.

### EXACT FIX — `src/backend/core/database.py`

Verify `get_cursor()` context manager does rollback on exception:

Find the `get_cursor()` context manager:
```python
@contextmanager
def get_cursor(self):
    conn = self._get_connection()
    try:
        cursor = conn.cursor()
        yield cursor
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        ...
```

If it's missing the `conn.rollback()` on exception, add it. This is the primary fix.

If the context manager already has rollback, then the partial failure scenario is prevented
by the transaction boundary. Verify this is the case.

### Also fix `_process_payment_for_specific_sales` in `credit_management.py`

This async function is called with `cur` passed as a parameter from inside a
`with db.get_cursor() as cur:` block. The function does additional DB writes using that
same `cur`. Since it's all within the same cursor context, rollback will cover all writes.

However: the function returns a response **without** the `with` block completing first
(because it's `await`ed and `async`). Verify the flow:

```python
with db.get_cursor() as cur:    # ← context opens
    ...
    return await _process_payment_for_specific_sales(cur, ...)
    # ← After return, context exits and commits
```

This is correct — `return` causes the `with` block to exit, which commits. ✓ No change needed
as long as `get_cursor()` has rollback on exception.

## BUG 9: Invoice number collision — two sales within same millisecond bucket get same invoice

### Root Cause
`src/backend/api/pos.py`:
```python
invoice_number = f"POS-{datetime.datetime.now().strftime('%Y%m%d')}{int(datetime.datetime.now().timestamp() * 1000) % 100000}"

```

```python
import secrets as _sec

```

In `hold_sale()`, find:

## BUG 10: `RateLimitMiddleware` uses in-memory dict — resets on restart, wrong on multi-worker

### Root Cause
`src/backend/core/security.py`:
```python
self.requests = defaultdict(list)
```
Rate limit counts are stored in memory. On server restart, all counts reset (rate limit bypass).
On multi-worker uvicorn, each worker has its own counter (rate limit is effectively N× the limit).

### EXACT FIX — `src/backend/core/security.py`

For a local desktop POS app, rate limiting should be light. Change to a more lenient limit
and add a note about the in-memory limitation:

Find:
```python
def __init__(self, app, max_requests: int = 1000, window_seconds: int = 60):
```
Change to:
```python
def __init__(self, app, max_requests: int = 5000, window_seconds: int = 60):
```

5000 requests/minute for a local app is reasonable (it prevents runaway loops but not
normal usage). The in-memory limitation is acceptable for a single-process desktop app.

Add a docstring note:
```python
class RateLimitMiddleware(BaseHTTPMiddleware):
    """
    In-memory rate limiter. Suitable for single-process desktop POS.
    NOTE: Counts reset on restart. For multi-worker deployment, use Redis-based limiting.
    """
```
